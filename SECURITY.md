# Security

## Threat model (v1)

**Adversaries we design against:**
- Opportunistic internet scanners hitting our public surface (Caddy, Telegram
  bot, n8n UI behind basic auth).
- A malicious or compromised dependency in our Python supply chain.
- A user mis-configuring a public-facing instance.
- A leaked Telegram bot token (whitelist still rejects messages from
  unknown TG IDs).

**Adversaries we explicitly do *not* design against** (v1):
- Nation-state actors.
- A motivated attacker with physical access to the VPS.
- Insider threats (single-user product; you are the insider).

## Threats per attack surface

The table below pairs each public-facing surface with the realistic
attacks against it and Mnemo's mitigation. Items marked **(deferred)**
are tracked for milestone-3.

| Surface | Threat | Mitigation |
|---|---|---|
| Caddy `:443` | TLS downgrade / mixed-content | Strict-Transport-Security 1-year HSTS in `Caddyfile.example`; automatic LE provisioning |
| Caddy `:443` | Clickjacking | `X-Frame-Options: DENY` blanket header |
| Telegram webhook | Replay of an old update | Telegram's own update IDs + bot dedupe (aiogram FSM) |
| Telegram webhook | Direct POST bypassing Telegram | URL contains per-install secret (`TELEGRAM_WEBHOOK_PATH`); 32 random bytes generated by `bootstrap.sh` |
| Bot → API | Stolen service JWT | 15-minute TTL; API-side rate limit (`RateLimitMiddleware`) caps blast radius; rotate `MNEMO_SERVICE_JWT_SECRET` to invalidate all live tokens |
| API ← n8n | Forged webhook callback | HMAC-SHA256 over body + timestamp; 5-minute replay window; `idempotency_keys` table for replay dedupe; hourly cleanup actor purges >24h-old rows |
| Postgres | SQL injection via user content | SQLAlchemy parameterised everywhere; ts_query uses `websearch_to_tsquery` (no raw concat); no `.execute(text("... " + var))` |
| Postgres | At-rest disclosure of integration creds | `integrations.config_encrypted` is AES-GCM (12-byte nonce + ciphertext). Key in `MNEMO_ENCRYPTION_KEY` only |
| LLM provider | Prompt-injected note exfiltrates other notes | RAG context only includes the requesting user's notes (Qdrant filter on `user_id`); the LLM cannot reach the API on its own; cited tokens are mapped back to the user's notes only |
| LLM provider | Runaway token spend | Per-user daily cap `MNEMO_USER_DAILY_TOKEN_CAP`; Prometheus `mnemo_llm_tokens_total` for alerting **(deferred — gauge present, no automatic cap)** |
| MinIO | Direct internet access | MinIO binds to `internal` network only; no Caddy route |
| n8n UI | Brute-force on basic-auth | Caddy basic-auth uses bcrypt hash; consider IP-allowlisting if your VPS supports it |
| Admin webapp | Same as n8n UI | Re-uses the n8n basic-auth credentials; read-only views (no DB writes) |
| Worker → MinIO | Path-traversal blob key | Blob keys are constructed server-side from `(user_id, UUID, sanitised filename)`; user input never controls the directory prefix |
| Backups | Plaintext dumps containing creds | `backup.sh` writes to `./backups/` on the host; you choose whether to encrypt before shipping off-host (rclone with `crypt:` recommended) |

## What's actually exposed to the internet

Only **Caddy** binds to `:80` / `:443`. Everything else (`api`, `bot`,
`postgres`, `qdrant`, `redis`, `minio`, `n8n`, `workers`) sits on an internal
docker network unreachable from outside.

Caddy proxies:

| route | target | auth |
|---|---|---|
| `POST /telegram/<bot_token_path>` | bot | shared-secret in URL path |
| `/n8n/*` | n8n UI | HTTP Basic Auth (set in `.env`) |
| `/admin/*` | webapp | HTTP Basic Auth (re-uses the n8n creds in v1) |

The Core API is **not** exposed publicly. Bot and webapp talk to it over the
internal network with a service JWT.

## Authentication

- **Telegram users:** whitelist in `MNEMO_ALLOWED_TG_IDS`. The bot rejects
  every update from a TG user not on the list — no `/start`, no `/help`,
  nothing leaks. The whitelist is the *only* gate; this is a single-user
  product by design in v1.
- **Service-to-service:** bot → API uses a service JWT signed with
  `MNEMO_SERVICE_JWT_SECRET`. Short-lived (15 min), rotated on every request.
- **Webhooks (API ↔ n8n):** HMAC-SHA256 over the body using
  `MNEMO_WEBHOOK_HMAC_SECRET`. Replay protection via the `idempotency_keys`
  table (5-minute timestamp window).

## Secrets

- `.env` is never committed. `.env.example` documents every variable.
- Integration credentials (Notion API keys, etc.) at rest in Postgres are
  encrypted with AES-GCM. The key lives in `MNEMO_ENCRYPTION_KEY` (32 bytes,
  base64). `scripts/bootstrap.sh` generates one if missing.
- Bot token, API keys, JWT secrets — all in `.env`, loaded by Pydantic
  Settings at boot. The app refuses to start if any required secret is empty
  or obviously default ("changeme", etc.).

## PII in logs

The default log level redacts user message bodies and shows only correlation
IDs. Set `MNEMO_LOG_PII=true` (off by default) to include bodies when
debugging — and remember to turn it off.

## Backups

`scripts/backup.sh` dumps Postgres (`pg_dump`), snapshots Qdrant via its API,
and mirrors the MinIO bucket. Output: `./backups/<UTC-timestamp>/`.
`scripts/restore.sh` does the reverse. Both are non-interactive and safe to
run from cron.

**Backups are NOT encrypted at rest** — they contain plaintext note
content and (briefly) encrypted integration creds + their encryption-key
identifier. Off-host them with `rclone crypt:` or your cloud provider's
SSE before treating them as anything other than local-disk-only.

## Rate limiting

Two layers, defense-in-depth:

1. **Bot side** (`ThrottleMiddleware`) — per-Telegram-user token bucket
   keyed in Redis. Default `MNEMO_THROTTLE_PER_MIN=10`. Rejects with a
   polite "🚧 slow down" reply.
2. **API side** (`RateLimitMiddleware`) — per-JWT-token (hashed) bucket,
   `throttle_per_min × 6` requests/minute (multiplier accommodates the
   pipelined capture + summarize + tag + embed call chain). Rejects with
   HTTP 429 + `Retry-After: 60`.

Both are exempt for `/v1/healthz`, `/v1/readyz`, and `/metrics` so a
storm doesn't break observability.

## Reporting a vulnerability

Email **security@example.com** (replace before publishing your fork). Include:

- Affected commit / version
- Reproduction steps
- Impact assessment
- Any PoC

We will acknowledge within 72 hours and aim to ship a fix or mitigation
within 14 days for high-severity issues. We do not currently run a bug
bounty program.

Please do **not** open a public GitHub issue for security reports.

## Known limitations

- **Single-tenant by design.** Hosting Mnemo for multiple distrusting users
  is unsupported in v1. The whitelist is the only authorization boundary.
- **No automatic rotation** of the AES-GCM encryption key. If you suspect
  `MNEMO_ENCRYPTION_KEY` was compromised, follow the rotation steps in
  `docs/upgrades.md`.
- **n8n UI on the same domain.** Behind HTTP Basic Auth, but a strong
  unique password is your responsibility. Consider IP-allowlisting it in
  Caddy if your VPS provider supports it.
